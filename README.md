# CRM by Romanychev — CRM мастера по ремонту техники

Одностраничное PWA-приложение (`index.html`) для мастера по ремонту бытовой
и холодильной техники: заявки клиентов, склад запчастей, финансы, клиенты,
статистика, арсенал инструмента. Работает полностью в браузере, без сервера
и без базы данных где-то в облаке.

Этот файл описывает, как всё устроено и как этим пользоваться, чтобы
поведение приложения не терялось «в голове» и не переизобреталось заново
при каждой правке.

## Где живут данные — это важно

Все данные (заявки, склад, расходы, клиенты, инструмент) хранятся **только
в браузере пользователя**, в `localStorage` (ключи вида `repair_*`), с
зеркальной копией в IndexedDB на случай, если `localStorage` неожиданно
очистится. Никакого сервера, аккаунта или облачной синхронизации нет.

Из этого следует:
- Данные привязаны к конкретному браузеру на конкретном устройстве. Тот же
  сайт в другом браузере или на другом телефоне — это **другой набор
  данных**, пустой.
- Очистка данных сайта в браузере, переустановка телефона/браузера,
  переход в приватный режим — данные теряются безвозвратно, если нет
  бэкапа.
- Обновление кода на GitHub (`main`) не трогает то, что уже сохранено у
  пользователя в браузере — правки логики применяются к тем данным, что
  уже лежат в `localStorage`, они не стираются при обновлении версии.

**Поэтому регулярный бэкап — не опция, а единственный способ не потерять
базу.**

## Резервные копии (бэкап)

### Как сделать бэкап
Кнопка «Скачать бэкап» (или `quickBackup()`) сохраняет один JSON-файл вида
`CRM_BT_backup_ГГГГ-ММ-ДД.json` со всем содержимым: заявки, склад, движения
склада, расходы, доходы, свои услуги, товарные чеки, цены чеков, арсенал
инструмента, черновик текущей заявки и настройки.

### Автобэкап
При каждом значимом действии (`maybeAutoBackup()`) приложение проверяет дату
последнего сохранённого бэкапа. Если прошло 7 дней или больше — само
предлагает браузеру скачать файл `CRM_BT_auto_*.json`. Отключается в
настройках (`autoBackup: false`), но по умолчанию включён.

### Восстановление из бэкапа
Кнопка «Восстановление» → выбрать `.json`-файл. Перед восстановлением
приложение **само** делает подстраховочный бэкап текущего состояния
(`before_restore`) — так что даже ошибочное восстановление не старого файла
можно откатить. После подтверждения все текущие данные полностью
заменяются данными из файла, страница перезагружается.

⚠️ Восстановление — это полная замена, не слияние. Если в файле нет какого-то
раздела (например, старый бэкап без «Арсенала»), этот раздел просто станет
пустым.

## Разделы приложения

- **Заявки** — карточка клиента, техника, диагностика, услуги, материалы
  (списываются со склада), сумма, статус (`В работе` / `Закрыта` / `Отказ`),
  гарантия, фото.
- **Склад** — позиции запчастей/расходников: остаток, средняя себестоимость,
  приход (с расходом или без), ручное списание, история движений,
  резервирование под открытые заявки.
- **Финансы** — список расходов (ручные + автоматические из закупок склада),
  статистика по деньгам.
- **Клиенты** — карточки клиентов, история их заявок, повторные обращения.
- **Статистика** — выручка, «на руки», расходы, остаток денег, топ услуг,
  расход материалов по складу, KPI по технике.
- **Арсенал мастера** — свой инструмент (не влияет на деньги заявок).

## Денежная модель заявки — как считается «На руки»

Это самая частая точка ошибок, поэтому расписано подробно. Вся логика — в
объекте `U` в `index.html` (`finalAmount`, `materialCost`,
`materialCostForExpense`, `expenseModel`, `profit`).

**Термины:**
- `sum` — сумма, которую озвучили клиенту.
- `discount` — скидка. `finalAmount = sum − discount`.
- `prepay` — предоплата (влияет только на `balance`, остаток к получению, не
  на прибыль).
- `expense_gray` («серый расход») — сумма, которую мастер **заявляет** как
  потраченную на ремонт, до деления с конторой.
- `expense_white` («белый расход») — официальная/фактическая себестоимость.
- `percent` — процент мастера от остатка после вычета серого расхода.
- материалы заявки — список деталей; каждая может быть привязана к позиции
  склада (`warehouseId`) с галочкой «Списать со склада» и режимом учёта
  (`exact` / `approx` / `presence`).

**Формула (`U.expenseModel`):**

```
materials = materialCostForExpense(заявка)   // см. ниже — не всё считается
actual    = white > 0 ? white : materials
declared  = gray  > 0 ? gray  : actual
margin    = declared − actual
base      = finalAmount − declared
profit    = base × percent / 100 + margin
```

`margin` — это разница между тем, что заявлено (`declared`), и тем, что
реально стоило (`actual`). Она **целиком** уходит мастеру сверх процента —
так исторически задумано (v19.2 в истории изменений), это специально, а не
баг.

### Правило от 2026-08-28: склад не тратится дважды

`materialCost(o)` — себестоимость **всех** материалов заявки, для
отображения (список заявок, форма заявки). Это просто справочная цифра.

`materialCostForExpense(o)` — то же самое, но **не считает** материалы,
которые физически списываются с уже оплаченного склада, то есть у которых
одновременно:
- есть `warehouseId` (материал выбран из позиции склада);
- включена галочка «Списать со склада» (`writeOff === true`);
- режим учёта не «только наличие» (`tracking !== 'presence'`).

Именно такие материалы уже создали расход **один раз** — в момент прихода
на склад (`addWarehousePurchase` → запись в «Финансы» с
`source: 'warehouse_purchase'`). Использование этой позиции в заявке должно
**только списывать количество со склада**, а не второй раз уменьшать
прибыль заявки через `expenseModel`.

Только `materialCostForExpense` используется внутри `expenseModel` — то есть
только она влияет на серый/белый расход по умолчанию и на «На руки».
`materialCost` (полная сумма) остаётся для информационных целей
(превью в форме заявки, список заявок, аналитика склада).

**Что при этом продолжает уменьшать расход заявки как раньше:**
- материалы, добавленные вручную **без** привязки к складу (деталь купили
  прямо под этот заказ, нигде больше расход не зафиксирован);
- позиции склада, где галочка «Списать со склада» выключена;
- материалы с учётом «только наличие» (`presence`) — по ним никогда не
  происходит автоматического списания остатка, поэтому их себестоимость
  больше нигде не фиксируется.
- ручные поля «серый»/«белый расход» и отдельная кнопка «Добавить расход»
  на вкладке «Финансы» — вообще не связаны с материалами, работают как
  раньше.

**Ограничение модели:** себестоимость склада — это **средняя** цена
(`item.price`, пересчитывается в `updateWeightedAverageCost`/
`recalculateWarehouseAverageCost`), а не отслеживание по партиям. Если
позицию один раз пополнили с суммой 0 (см. «Пополнение без финансового
расхода» ниже), а потом ещё раз — уже с реальной суммой, средняя
себестоимость посчитается по оплаченным приходам и применится ко **всему**
текущему остатку этой позиции, включая бесплатные единицы. Для точного
партийного учёта в приложении сейчас нет механизма — используется общая для
всех операций модель «средней себестоимости».

## Правила склада

- **Приход с суммой** (`addWarehousePurchase`, сумма > 0) — увеличивает
  остаток, пересчитывает среднюю себестоимость, создаёт расход «Закупка
  склада» в «Финансах», связанный с этой позицией (`warehouseId`).
- **Пополнение без финансового расхода** (сумма = 0) — увеличивает остаток,
  **не** создаёт расход и **не** меняет среднюю себестоимость. Используется,
  когда деньги на эту позицию уже потрачены раньше (до начала работы с этой
  CRM) или потрачены не важным для отчётов образом, и учитывать их как
  расход текущего периода не нужно.
- **Ручное списание** (`manual_out`) — просто уменьшает остаток без связи с
  расходами и заявками, для инвентаризации/коррекции.
- **Списание по заявке** (`order_out`) — создаётся при закрытии заявки для
  материалов с `writeOff === true`, уменьшает остаток на складе. Не создаёт
  запись в «Финансах» — только движение склада, себестоимость которого видно
  в статистике отдельной строкой («Израсходовано в ремонтах»), но не
  вычитается из денег повторно (см. правило выше).
- **Возврат по заявке** (`order_return`) — если заявку с уже списанными
  материалами вернули из статуса «Закрыта» обратно в работу, остаток
  возвращается на склад.
- **Отмена прихода** — можно отменить последнюю закупку (если она ещё не
  израсходована/зарезервирована), это отменяет и связанный расход в
  «Финансах».
- **Резервирование** — материалы открытых (незакрытых) заявок резервируют
  количество на складе, чтобы его нельзя было списать дважды в разные
  заявки.

## Разработка

- Весь код — один файл `index.html` (HTML + CSS + JS), без сборки и
  зависимостей. Открывается прямо в браузере.
- `manifest.json` + `sw.js` — PWA: иконка на телефоне, работа как отдельное
  приложение. Service worker использует стратегию «сначала сеть, кэш —
  запасной вариант» (`fetch(..., {cache:'no-store'})`), поэтому при наличии
  интернета пользователь всегда получает актуальную версию сразу после
  обновления `main`, без необходимости вручную сбрасывать кэш.
- История изменений версий — кнопка «История изменений» в приложении
  (`showChangelog()`).
